# ADR-0033: Mode Transitions — What a New Cursor Inherits

- **Status:** Accepted
- **Date:** 2026-09-11
- **Context:** The usual onboarding path is a full (often keyset) load, then `mode: incremental` on the same export. `export_state` holds one cursor per export NAME, so a field switch on 0.25.0 — keyset on `idvisit` → incremental on `visit_last_action_time` — compared the new column against the old key's value: on MySQL a silent zero-row match, on every run, with exit 0. This ADR fixes what a transition may inherit.

---

## Definitions

| Term | Meaning |
|------|---------|
| **Cursor identity** | What a persisted cursor value refers to: the incremental `cursor_column`, `coalesce(primary,fallback)` in coalesce mode, or the keyset `chunk_by_key`. Stored in `export_state.cursor_column` (state schema v26). |
| **Carrying mode** | A mode that persists a cursor: `incremental`, and keyset (`chunk_by_key`) in every variant — sequential, parallel, with or without `chunk_checkpoint`, `keyset_incremental`. |
| **Progress key** | Whose stored progress a run reads and writes, computed once from the resolved plan (`ResolvedRunPlan::progress_key`, added 2026-10-07): the export name and source key select the row; the stream (MT8) and the cursor identity are compared before use. A runner reads stored progress only through the claim `StateStore::claim` grants for that key. |
| **Non-carrying mode** | `full`, `time_window`, range `chunked` (`chunk_column`) — no cursor is persisted. |

---

## Contract

| ID | Name | Statement | Enforced by |
|----|------|-----------|-------------|
| **MT1** | No cursor, full pass | After a non-carrying mode the first incremental run exports every row. The overlap with the full load is at-least-once; the warehouse dedups by key. | `ProgressClaim::cursor` on an empty row |
| **MT2** | Same identity continues | After a carrying mode, a run with the SAME identity continues past the stored value: keyset → incremental on the key, incremental → `keyset_incremental` on the column, adding `settle`. | `ExtractionStrategy::cursor_identity` equality |
| **MT3** | Different identity refuses | A run with a DIFFERENT identity fails before exporting anything, naming both identities and `rivet state reset`; after the reset it is a full pass (MT1). Changing `incremental_cursor_mode` changes the identity. | `ProgressClaim::cursor` |
| **MT4** | Writers record identity | Every cursor write records its identity: the incremental commit and the keyset page checkpoint / final high-water. | `StateStore::update_with_column` via `RunStore::commit` and `run_keyset` |
| **MT5** | Legacy keyset cursors | A pre-v26 cursor (no identity) is attributed to the latest successful keyset run when that run's `cursor_max` equals the stored value; MT2 / MT3 then apply. | `StateStore::legacy_cursor_owner` |
| **MT6** | Legacy incremental cursors (gap) | A pre-v26 cursor written by `incremental` has no recoverable identity — no column in state, metrics or the run journal — so a changed `cursor_column` is not detected. Reset when changing the cursor of an export whose last run predates v26. | — (documented gap) |
| **MT8** | Another stream refuses | Stored progress (cursor, keyset high-water, Mongo `resume` `_id`, interrupted-run anchor) records its STREAM: the first relation the query's outermost `FROM` names, quotes stripped (`table:` and `query:` alike). A run that would continue from progress recorded for a provably different relation is refused before anything is read or written (`RIVET_STATE_CURSOR_STREAM_MISMATCH`, exit 5), whether one export was repointed or two exports share a name in one state database. A bare name and its qualified form are the same relation; a `FROM` that names none (a subquery) is not checked. A stale high-water no clean run seeks from (keyset without `keyset_incremental`) is not progress. Progress written before state v33 names no stream: the first run adopts the relation it reads and says so (amended 2026-10-06). Amended 2026-10-08: the stream also records the PostgreSQL `search_path` the source URL sets (an unqualified name under a one-schema path is that schema's table; the same bare name under another path is another stream) and the ROWS the query selects (the query without its projection and its `FROM` relation, lower-cased, whitespace folded outside quotes), so an edited filter, join or CTE is another stream while a changed column list, letter case or layout is not; a row that holds neither yet adopts the ones the export has now. The source key that selects the row always names the port (the engine's default when the URL leaves it out), and progress stored under the other spelling is moved onto it. Amended 2026-10-08 (owner): the ROWS are read from the query as written, before `${...}` substitution, so a `--param` or environment value that changes between runs is not an edit and neither refuses nor warns, while an edit of the text around the placeholder is one (`ResolvedRunPlan::query_template`; a plan sealed before that field carries its substituted query, and a substituted query that fills the placeholders of a query as written is the same rows, in either order). A refused edit that is meant has a third way out beside restore and reset: `rivet state accept -c <config> --export <name>` re-binds the stream, schema and rows of that one row to what the export reads now and keeps the cursor value, its column and any anchor (`StateStore::accept`); it is per export and per edit, never a setting, it refuses a cursor written for another column, and each acceptance is a `run_journal` row with status `accepted`. | `StateStore::claim` in `execute_resolved_plan`; `sql::outer_from_relation`, `sql::row_set`, `SourceConfig::search_path`, `canonical_source_key` |
| **MT9** | An interrupted run belongs to its mode | (2026-10-07) A stream's stored record is one of two KINDS: a committed high-water (every row at or below it is in a manifest; MT2 lets any mode with the same identity continue it) or an interrupted checkpoint run, owned by the mode that opened it (`keyset`, or `chunked` for a range-chunk run, which anchors on the same row). A run of ANOTHER mode that meets an interrupted run fails before reading anything, naming the run, its mode and both remedies: restore that mode's settings and finish the run, or abandon it (`rivet state reset` for a keyset run, `rivet state reset-chunks` for a range-chunk run), after which the next run is a full pass (`RIVET_STATE_INTERRUPTED_RUN_OWNER_MISMATCH`, exit 5). An interrupted range-chunk run is found by export name AND source key, so a same-named export of another source never resumes it. A chunk run left by a version that recorded no source is adopted once, with a warning, by the only source that export name has progress under; when the name has progress under more than one source it is refused (`RIVET_STATE_CHUNK_RUN_OWNER_UNKNOWN`, exit 5) until `rivet state reset-chunks`. | `StateStore::claim`, `ProgressClaim::chunk_run` |
| **MT10** | An interrupted run is continued only with its checkpoint | (2026-10-08) What continues an interrupted run is a run of its mode whose plan keeps the checkpoint (`chunk_checkpoint`, `keyset_incremental`, MongoDB `source.mongo.resume`). A run of the SAME mode without it reads from the start, would finish beside the interrupted run, and a later checkpointed run would then resume that older run over parts read before the finished one (exit 0, 14 of 20 changed rows: main and 0.31.0). It is refused like another mode is (MT9: same code, exit 5, nothing read or written), naming the run and both remedies: restore the checkpoint setting and finish the run, or abandon it. An interrupted range-chunk run is found in `chunk_run` by export name and source whether or not the stream row still anchors it, so `rivet state reset` (which clears the row, not the chunk run) and a run left by a version that anchored nothing do not hide it from MT9 or MT10. State written by 0.31 and earlier may already hold a chunk run that a later run finished beside: a chunk run that recorded no source, with a successful run of its export recorded after it was opened, is refused for every plan (`RIVET_STATE_CHUNK_RUN_SUPERSEDED`, exit 5) until `rivet state reset-chunks`. | `StateStore::claim` (`refuse_unfinished_run`), `StateStore::finished_after_unsourced_chunk_run` |
| **MT7** | Load follows the export | `rivet load` follows what each run holds. A run that re-read the whole table — `full` / `chunked` / `time_window`, or an incremental run with no cursor to resume from — OVERWRITES `<table>` (amended 2026-10-03: not a run that continues past its last key — chunked `keyset_incremental`, Mongo `source.mongo.resume` — which is a delta and appends like one), and only a table rivet's ledger says it loaded, with the partitioning and clustering the config declares; anything else (a foreign table, a hand-reshaped one, a view left by an append mode) fails naming the difference, and nothing is changed. A delta (`incremental` with a cursor, `cdc`) appends to `<table>__changes` behind a `<table>` view; the first delta over a `<table>` table renames it to `<table>__changes` (rows, partitioning and clustering kept; `__op` / `__pos` / `__seq` added as NULL) — no copy, nothing dropped. It refuses, touching nothing, when rivet did not load the table, its columns differ from the export's, or a `<table>__changes` already exists beside it. | `load::adopt_full_load_table` and `load::ensure_overwritable` in the shared drivers |

## Evidence

`docs/mode-transition-matrix.yaml`: every transition × engine is a live test in `tests/live/live_mode_transition.rs`. Each runs the previous mode over 10 rows through the Rig, inserts 3 more, restages the same Rig (same state DB) to the new mode, runs it and re-reads the destination. MT3 cells are RED on the 0.25.0 binary (`RIVET_BIN_OVERRIDE`).
